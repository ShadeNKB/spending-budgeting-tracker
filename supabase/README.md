# supabase/

The relay for SpendTrack's optional cross-device sync: one table, `public.sync_buckets`, with one row per sync code. Every file here is applied **by hand, in order, in the Supabase SQL editor**.

> **Do not point `supabase db push` (or any other migration runner) at this folder.** The `*.rollback.sql` files sit beside the migrations and carry the same numbers, so a runner would take them for migrations and run them too. Nothing here is recorded in Supabase's migration history either: a runner would try to apply everything again.

Step by step, with the expected output of every step, STOP points and rollback: [`docs/brain/sync-runbook.md`](../docs/brain/sync-runbook.md).

## `migrations/`

| File                               | What it does                                                                                                                                                                                                                                                                                                                         | When                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `001_sync.sql`                     | Creates the table, adds it to the Realtime publication, leaves row level security off and grants the public (`anon`) key SELECT, INSERT and UPDATE.                                                                                                                                                                                  | First.                                                                                                                                               |
| `002_sync_indexes.sql`             | Adds `created_at`, an index on `updated_at`, and a manual prune function, `prune_stale_sync_buckets()`.                                                                                                                                                                                                                              | After 001.                                                                                                                                           |
| `003_harden_prune_search_path.sql` | Pins the prune function's `search_path`.                                                                                                                                                                                                                                                                                             | After 002.                                                                                                                                           |
| `004_sync_rpc.sql`                 | Takes DELETE, TRUNCATE and the prune function away from `anon` and `authenticated`; refuses new writes with a non-UUID id, a payload that isn't an object of at most 2 MiB, or a non-finite `updated_at`; adds the sync functions `st_sync_head`, `st_sync_pull` and `st_sync_push`. Additive: every SpendTrack build keeps working. | Gate C. Then the app may use the functions (`VITE_SYNC_RELAY=auto`) and compare-and-set (`VITE_SYNC_CAS=on`, after `scripts/verify-cas.mjs` passes). |
| `004_sync_rpc.rollback.sql`        | Removes the three functions, the three write checks and the index. Keeps the revokes. Refuses to run while 005 is applied.                                                                                                                                                                                                           | Only to undo 004.                                                                                                                                    |
| `005_sync_lockdown.sql`            | Removes every table privilege from `anon` and `authenticated`, turns row level security on with no policies (only the functions reach the table), takes the table out of the Realtime publication and sets replica identity back to default. Refuses to run unless 004 is complete.                                                  | Gate E: when every device uses the functions and Settings › Sync says "Ready for the database lockdown."                                             |
| `005_sync_lockdown.rollback.sql`   | Puts back the state after 004. Reopens the table to the public key.                                                                                                                                                                                                                                                                  | Only to revive a device that can't update.                                                                                                           |

Every migration and rollback runs in one transaction, can be run again safely, and never changes or deletes a row.

## `checks/`

| File                         | What it does                                                                                                                                                                         | When                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| `000_preflight_readonly.sql` | One read-only `SELECT`: the stage (`before 004`, `004 applied`, `005 applied` or `mixed`), counts, privileges and a `GO` or `STOP` verdict. It never shows a sync code or a payload. | Before each gate, and after 004. |
| `004_verify.sql`             | Checks the state 004 leaves, then exercises the functions as `anon` on throwaway rows and undoes every row it wrote. Row 0 is the `RESULT`.                                          | After 004.                       |
| `005_verify.sql`             | The same for 005: no table access for `anon`, row level security on, the functions still work.                                                                                       | After 005.                       |

[`scripts/verify-cas.mjs`](../scripts/verify-cas.mjs) checks the same through the API the app uses: compare-and-set on a throwaway row after 004, and `--lockdown` after 005. Only the owner runs it, against his own project.

## How these files are tested

Nothing in this folder is tested against a live project. The unit tests in [`src/__tests__/sql/`](../src/__tests__/sql) apply every file, in order and twice, to a fresh real Postgres (PGlite, a dev-only dependency) with Supabase's roles and default privileges emulated, run each check, and run 0.11.0's sync transport against the result. [`scripts/verify-cas.pg.test.mjs`](../scripts/verify-cas.pg.test.mjs) runs `scripts/verify-cas.mjs` against the same database, before 004, after 004 and after 005, and the runbook's optional cleanup SQL with it.

What that cannot show stays a check in the runbook:

- **The Postgres version.** The tests run on PostgreSQL 18 (PGlite 0.5.10); a Supabase project runs 15 or 17. The one difference these files meet, the `MAINTAIN` privilege (17 and later), is guarded, and the tests also run every file with that guard off. The preflight's `postgres_version` row records the live version.
- **Two devices writing at the same moment.** PGlite has one connection, so no race is executed. `st_sync_push` reads the token under a row lock and matches it again in its `UPDATE` (either alone keeps two crossing writes from both landing), and takes an advisory lock before the creation caps, then looks the row up again under it (a create that lost a race to the same row is a conflict, never "full"); a test pins those lines.
- **PostgREST, Realtime, `pg_cron` and the dashboard**: the runbook checks them on the live project.

## Known limitations

- **The creation caps are global.** After 005, anyone with the public key can still create rows through `st_sync_push` with random ids, up to the caps (20 an hour, 500 rows). At 500, every new sync code is refused (53400) until rows are removed; existing codes keep syncing. Nothing prunes yet: see the runbook's "Later, optional".
- **The database can still be filled (F-068's size impact is narrowed, not closed).** 004 closes F-068's delete, truncate and prune holes and refuses bad ids, shapes and oversized writes; it does not bound the relay's total size. Until 005, `anon` keeps table INSERT, which the creation caps don't see, so any number of rows of up to 2 MiB of jsonb text can be written. After 005 the caps count rows, not bytes: 500 rows × 1,258,291 bytes is about 600 MiB of jsonb text (random text doesn't compress), over the free plan's 500 MB, reachable in about 25 hours at 20 creates an hour. Forced and compare-and-set writes to rows an attacker created have no rate limit either, and each leaves a dead TOAST value behind until vacuum. Over 500 MB, Supabase makes the project read-only and sync stops; no data is lost (every device keeps its full copy). A firmer bound (a byte budget under the create lock, a lower row cap, or sync behind sign-in) is a later change; the runbook tells the owner what to watch.
- **A table write refused by `sync_buckets_payload_bounded` (23514)** is retried as a server error by 0.11.0 instead of pausing as "too large". Only a build on the table path can meet it (between 004 and the `VITE_SYNC_RELAY=auto` redeploy, or an older build), and only with more than 2 MiB of jsonb text: about 2.3 bytes per character on average under the app's 900,000-character limit, so mostly CJK text.
- **The app's own setup steps** (Settings › Sync when no relay is configured) still name only `001_sync.sql`. Apply 001 to 004 in order, as above.
